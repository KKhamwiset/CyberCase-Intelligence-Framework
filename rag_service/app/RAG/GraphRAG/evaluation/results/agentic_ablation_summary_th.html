Agentic RAG — self-reflection loop ช่วยหรือทำให้แย่ลง

สรุปผลการทดลอง ablation และการแก้ไข pipeline สำหรับ CyberCase Intelligence Framework

ชุดข้อมูล: real-CTI tier 100 เหตุการณ์ (347 attack steps: named 61 / described 286) gold จาก CTID + CISA โมเดล: openai/gpt-5.6-luna ผ่าน OpenRouter Branch: eval/agentic-ablation วันที่: 17–19 กันยายน 2569 ค่าใช้จ่ายรวม: 1.23 USD (1,058 LLM calls)

1. สรุปผู้บริหาร

  • ของเดิมที่ serve อยู่ self-reflection loop ทำให้คะแนนแย่ลง เปิด loop ได้ macro F1 0.629 ส่วนปิด loop ได้ 0.693 ต่างกัน −0.064 (95% CI [−0.113, −0.021], p = 0.012) ทั้งที่จ่ายเพิ่ม 1.5 LLM call และ 15 วินาทีต่อเหตุการณ์
  • ต้นเหตุคือ ACKNOWLEDGE_LIMIT ทิ้งบทวิเคราะห์ 10 จาก 100 เหตุการณ์ถูกแทนที่ด้วยข้อความ "ข้อมูลไม่เพียงพอ" ทั้งที่ครึ่งหนึ่งมี gold ครบอยู่ใน context แล้ว เสีย F1 เฉลี่ย −0.704 ต่อเหตุการณ์
  • แก้ 2 จุดแล้วได้ผล หลังแก้ macro F1 ขึ้นเป็น 0.705 และ recall 0.794 ทำให้การเปิด loop ดีกว่า ปิด loop อย่างมีนัยสำคัญ (+0.012 F1, p = 0.030; recall +0.029, p = 0.002 ชนะ 10 เสมอ 90 แพ้ 0)
  • fast path ที่ดูคะแนนใกล้เคียงกันนั้นไม่ grounded เทคนิคที่ fast path ตอบถูก 60% ไม่ปรากฏใน context ที่ retrieve มาเลย โมเดลตอบจากความรู้ในตัวเอง เทียบกับ agent ที่อยู่ที่ 1%
  • วิธีที่ทดลองแล้วไม่ได้ผล การให้ evaluator อ่าน context ทั้งหมดแทน 4000 ตัวอักษรแรก ทำให้ตรวจจับ context ที่ขาดข้อมูลได้ แย่ลง (detector F1 0.442 → 0.277) จึงไม่นำมาใช้

4.1 ACKNOWLEDGE_LIMIT ทิ้งบทวิเคราะห์ทั้งก้อน

  • เกิดหลัง broaden 1 รอบทั้ง 10 ครั้ง ไม่ใช่ตั้งแต่รอบแรก แปลว่าจ่ายค่า LLM เพิ่ม 2 call เพื่อให้ได้คำตอบที่แย่ลง
  • 5 ใน 10 ครั้งนั้น context มี gold ครบ 100% อยู่แล้ว
  • ข้อความที่ตอบกลับอ้างว่าขาด "Initial Access, Credential Access, Impact" ซึ่งเป็น phase ใน prompt ไม่ใช่เทคนิคที่เกิดในคดี

4.2 broaden แค่สลับของ ไม่ได้เพิ่มข้อมูล

  • context รอบแรกยาวเฉลี่ย 9,258 ตัวอักษร จากเพดาน 10,000 คือเต็มอยู่แล้ว
  • รอบสองใช้เพดานเดียวกัน ผลลัพธ์จึงเบียดของเดิมออก: gold recall 0.761 → 0.759 (ดีขึ้น 6 เท่าเดิม 13 แย่ลง 6 แย่สุด −0.33)
  • บน 25 เหตุการณ์ที่ loop ทำงาน A แพ้ B ถึง −0.257 F1 (95% CI [−0.422, −0.095])

9. ข้อจำกัดของผลการทดลอง

  • B, F และ M แตกกิ่งจากรอบของ A ไม่ใช่การรันแยก ข้อดีคือส่วนต่างสะท้อนเฉพาะสิ่งที่แก้ ข้อเสียคือค่าเฉลี่ยทั้งชุดถูกเจือจางโดยเหตุการณ์ที่ส่วนที่แก้ไม่ได้ทำงาน
  • B − C ไม่ใช่ผลของ decomposition อย่างเดียว เพราะ query_fast ใช้ context เล็กกว่าและไม่เรียก router ด้วย
  • decomposer ไม่ deterministic แม้ตั้ง temperature 0 การรันซ้ำให้ sub-queries ต่างกัน และ verdict ของเหตุการณ์ก้ำกึ่งพลิกได้ (เทียบ smoke run: ตรงกัน 4 จาก 5)
  • รัน arm ละครั้งเดียว การเทียบที่มีการสร้างคำตอบใหม่จึงมี noise ปนอยู่ ซึ่ง CI สะท้อนไว้แล้วแต่แยกออกจากกันไม่ได้
  • การนับเทคนิคใช้เฉพาะ ID ที่คำตอบอ้างถึง เทคนิคที่อธิบายด้วยถ้อยคำโดยไม่ระบุ ID จะไม่ถูกนับ ส่วนการจับคู่ด้วยชื่อใช้ไม่ได้เพราะ alias map ชี้ชื่อที่ซ้ำกันไปที่ ID ของ mobile (เช่น "screen capture" → T1513 แทน T1113)
  • gold 1 ID (T0827) เป็นเทคนิคฝั่ง ICS ซึ่งไม่ได้ ingest ไว้ ทุก arm จึงหาไม่เจอเท่ากัน

10. สิ่งที่ยังเหลือ

วิธีที่ 2 (rubric ตาม sub-query) ตรวจจับได้ดีขึ้นชัดเจนในระดับ probe และตอนนี้ broaden ไม่ทำข้อมูลหายแล้ว ความเสี่ยงเดิมจึงหมดไป เหลือการวัด F1 แบบ end-to-end ซึ่งต้องรันใหม่ทั้ง 100 เหตุการณ์ ประมาณ 550 calls, 0.55 USD, ราว 2 ชั่วโมง
