# เรื่อง grammar ทั้งหมดในที่เดียว (2026-10-01)

บันทึกวันที่ 2026-10-08: เปลี่ยนทุก structured stage ของ backend เป็น JSON contract
ใน system prompt และตรวจด้วย Pydantic หลังตอบแล้ว ไม่ส่ง `output_config` ไปบังคับ grammar
อีกต่อไป ครอบคลุม assessment, Reading, Judgement, Views, Chat และ LLM MITRE gate.
ผลทดลองและตัวเลขด้านล่างเป็นของ Reading ในการทดลองเดิมเท่านั้น ไม่ใช่ผลวัดของทุก stage
หลังการเปลี่ยนครั้งนี้ รายละเอียดปัจจุบันอยู่ที่ `backend/ARCHITECTURE.md` ส่วน 5.

## สรุปสั้น

- **ปัญหา:** ตอนให้ provider บังคับ JSON ด้วย grammar ขั้น reading บางครั้งเขียนแต่ช่องว่างจนหมด token ทำให้เคสล้ม ช้า และแพง
- **สาเหตุ:** schema บังคับ key ที่โมเดลไม่คาดว่าจะต้องเขียน grammar จึงห้าม `}` แต่ยอมให้เขียนช่องว่างได้ไม่จำกัด
  โมเดลเลยวนเขียนช่องว่างอยู่ที่เดิม
- **ทางแก้:** reading ไม่ใช้ grammar อีกต่อไป
  - บอกหน้าตา JSON ไว้ใน prompt
  - ให้โค้ดตรวจหลังโมเดลเขียนเสร็จ
  - ถ้าไม่ผ่าน ถามใหม่ได้หนึ่งครั้ง
- **ผล (100 เคส, 151-250):** ล้มลดจาก 4 เป็น 1, runaway ลดจาก 18 เป็น 1, เวลาลดจาก 253 เป็น 136 วินาทีต่อเคส,
  ค่าใช้จ่ายลด 34% และคุณภาพไม่แย่ลง
- **ใช้งานจริงแล้ว:** PR #43 merge เป็น commit `8750cbc` แล้ว prompt ที่ใช้ตรงกับที่ทดสอบทุกไบต์
  **เรื่องนี้ไม่ต้องรันอะไรใหม่**

## 1. grammar คืออะไร

- เราสั่งโมเดลผ่าน OpenRouter และส่ง JSON schema ไปด้วย
- provider บังคับให้ทุก token ที่โมเดลเขียนต้องเข้ากับ schema (constrained decoding) token ที่ผิด schema จะถูกห้าม
- ข้อดี: ได้ JSON ที่ถูกรูปเสมอ
- ข้อเสียที่เราเจอ: อ่านข้อ 2 และ 3

## 2. อาการ

- **โมเดลเขียนแต่ช่องว่าง:** เขียน JSON ไปได้สักพัก แล้วเหลือแต่ช่องว่างกับขึ้นบรรทัดจนถึงเพดาน 40,800 token
- **เกิดบ่อยแค่ไหน:** 14-30% ของ reading ครั้งแรก แล้วแต่ชุด ถ้าเกิดสองครั้งติดกัน เคสนั้นล้ม ราว 4-5% ของการวิเคราะห์
- **ต่อหนึ่งครั้งที่เกิด:**
  - ช้าลง: ใช้เวลากลาง 10 นาที สูงสุด 25 นาที ปกติใช้ 2.2 นาที
  - แพงขึ้น: ราว USD 0.012 ปกติราว 0.003

## 3. สาเหตุ

**กลไก:**

```
โมเดลเขียน quote เสร็จ แล้วคิดว่า object จบ จะเขียน: ขึ้นบรรทัด, เว้นวรรค, }
  -> ขึ้นบรรทัดและเว้นวรรค: grammar ยอม
  -> }: grammar ห้าม เพราะ schema ยังบังคับ key ต่อ (เช่น document_id)
  -> ตัวเลือกที่เหลือมีแค่ช่องว่าง หรือ , ตามด้วย key ที่โมเดลไม่ได้ตั้งใจเขียน
  -> ช่องว่างชนะ เพราะเป็นส่วนต้นของสิ่งที่โมเดลจะเขียนอยู่แล้ว
  -> เขียนช่องว่างแล้ว สถานะไม่เปลี่ยน ก็ย้อนกลับไปจุดเดิม วนจนหมด token
```

**ทำไมโมเดลไม่รู้ว่ายังมี key:** Gemma บน vLLM มองไม่เห็น schema เห็นแค่ prompt และ prompt เดิมพูดถึง key ไม่ครบ

**หลักฐาน:**

| หลักฐาน | บอกอะไร |

## 7. ต้องรันใหม่ไหม

**ไม่ต้อง** สำหรับข้อสรุปในเล่ม เพราะ:
- prompt ที่ใช้งานจริงคือตัวเดียวกับที่ยืนยันแล้ว ตรงกันทุกไบต์
- เราเก็บสิ่งที่โมเดลเขียนไว้ทุกเคส การแก้ที่อยู่หลังโมเดล (binder, scorer) เอาผลเดิมมาคำนวณใหม่ได้โดยไม่เสียเงิน

**ที่เสียเงินและควรพิจารณา (ไม่ใช่ตัวเลขของเล่มเรื่อง grammar):**
1. **ทดสอบกับคดีไทยสมมติ 5 เคส (ราว $0.05):** เช็คความปลอดภัยของ production เพราะระบบจริงใช้ภาษาไทย และเคยเห็นว่าตัวอักษรที่ไม่ใช่ ASCII เสียได้
2. **โมเดลตระกูลที่สอง (cap $2):** ดูว่าผลไม่ได้ขึ้นกับ Gemma
3. **ภายหลัง:** judgement ยังใช้ grammar อยู่ (runaway 3 ครั้งแต่รอดทั้งหมด) ถ้าจะแก้แบบเดียวกัน prompt ต้องเปลี่ยน และต้องรันยืนยันใหม่

## 8. พูดได้ / พูดไม่ได้

**พูดได้:**
- ในงานของเรา (Gemma 4 ผ่าน OpenRouter, schema ยาวซ้อนหลายชั้น) การบังคับ JSON ด้วย grammar ทำให้ reading วนเขียนช่องว่างจนเคสล้ม
- การให้โค้ดตรวจหลังเขียนแทนทำให้ปัญหานี้หาย โดยคุณภาพไม่แย่ลง
- การบอก layout ใน prompt ทั้งที่ยังใช้ grammar หยุดการวนได้ แต่ทำให้ตัวอักษรใน quote เสีย

**พูดไม่ได้:**
- grammar ทำแบบนี้กับทุกโมเดลหรือทุก engine (เรามีแค่ Gemma และไม่รู้แน่ว่า provider ใช้ engine อะไร)
- แก้ที่ prompt อย่างเดียวก็พอ (ยังไม่ได้ทดสอบแบบที่สะอาด)
- ใช้ได้ดีกับภาษาไทย (ยังไม่ได้ทดสอบ)
