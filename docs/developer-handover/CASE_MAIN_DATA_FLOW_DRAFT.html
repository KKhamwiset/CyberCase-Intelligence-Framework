Case-first main data flow

Draft นี้แยกเส้นทางของ Case analysis, optional Chat Q&A และ clarification follow-up ให้เห็นว่า payload ไหนเป็น evidence, payload ไหนเป็น derived result และจุดไหนที่ระบบต้องหยุดก่อนทำงานต่อ

Case owns the durable work

Case เป็นเจ้าของ documents, admitted evidence, immutable snapshot, CaseRun, validated analysis result และ clarification state การกด Analysis จึงเรียก Case API โดยตรง ไม่ต้องสร้างหรือส่ง Chat message ก่อน

Chat is optional interaction

Chat เป็น transcript และ Q&A เพิ่มเติม หลังมี validated analysis แล้วเท่านั้น ผล analysis ที่สำเร็จถูก publish เป็น assistant message ได้ แต่ message ไม่กลายเป็น authoritative evidence เอง

ภาพรวม ownership และ hand-off

one case · two interaction modes

ภาพรวมที่ต้องจำ: POST /analysis ไม่ได้อยู่ใต้ Chat และ Chat ไม่ใช่ตัวสร้าง CaseRun analysis อีกต่อไป ผล analysis ที่ validate แล้วจึงค่อยถูกเก็บเป็น Case result และ publish เป็น assistant message เพื่อให้เปิด Chat แล้วเห็นผลเดียวกันได้

1. User กด Add file

untrusted extraction → explicit admission

Output: upload คืน CaseDocumentRead ที่มี extraction preview; ขั้นนี้ยังไม่สร้าง evidence และยังไม่เริ่ม CaseRun การกด Admit reviewed text จึงเป็น gate แยกที่สร้าง EvidenceSource/EvidenceRevision แบบ immutable

2. User กด Analysis

evidence snapshot → validated Case result

Gates: ต้องมี admitted evidence, ต้องไม่ชน active CaseRun และต้องผ่าน idempotency/fingerprint กับ expected evidence revision จากนั้น worker จึง bind exact quote/citation กับ snapshot ได้ หาก trace ไม่ valid ให้ fail closed; MITRE เป็น optional technical augmentation และ skip / no-match / failure ต้องยังถูกบันทึกเป็น outcome แยกจาก core analysis

3. User พิมพ์ Chat ถามตอบ

optional Q&A over pinned analysis

Gates: ordinary composer ส่ง action=ask เสมอ ถ้าไม่มี validated result จะได้ analysis_required (412) และไม่แอบเริ่ม analysis ถ้ามีผลแล้ว backend จะ pin CaseAnalysisResult + CaseEvidenceSnapshot, ตรวจ trace/citations และใช้ history เดิมของ result ได้ไม่เกิน 12 ข้อความ Q&A นี้ไม่เพิ่ม evidence, ไม่เรียก RAG และไม่แก้ผล analysis หลัก

4. Follow-up ระหว่างระบบกับ User

clarification answer → new authoritative analysis

Canonical follow-up: analysis สร้าง durable clarification gap → Case Overview แสดงคำถาม → User ตอบผ่าน answerCaseClarification → backend admit คำตอบเป็น clarification_answer evidence revision → enqueue analysis ใหม่ ผลเก่ายังเป็น historical result และผลใหม่จึงถูก publish กลับ Case/Chat

Chat boundary: composer ปกติไม่ควรตอบ clarification เอง และไม่ควรเปลี่ยนข้อความธรรมดาให้เป็น evidence โดยอัตโนมัติ

Compatibility: Case Chat ยังรับ action=add_case_info แบบ explicit ได้เมื่อมี pending clarification แต่เป็น compatibility path; ownership และ admission ยังอยู่ที่ Case clarification service

Gates ที่ทำให้ flow หยุด

fail closed where evidence or binding is uncertain

Evidence readiness

ไม่มี admitted source หรือ text ว่าง → upload/admit หรือ Analysis ต้องหยุด ไม่สร้างผลลัพธ์จาก extraction preview

Ownership and binding

Case, snapshot, result, thread และ source ต้องสัมพันธ์กันจริง ถ้า cross-case, unknown ID หรือ hash ไม่ตรง → reject

Run admission

active CaseRun, stale expected revision, fingerprint conflict หรือ retry ที่ไม่ใช่ logical request เดิม → ไม่รับซ้ำ

Exact provenance

citation ต้อง resolve กับ source/revision/exact quote/page span ที่พิสูจน์ได้เท่านั้น ambiguous หรือ invalid trace → fail closed

Conditional MITRE

technical context ไม่เกี่ยวข้อง → skip; mapping ว่าง/partial/failure → แสดง outcome แยก ไม่ยกระดับ external row เป็น evidence

Chat context

ยังไม่มี completed validated analysis → 412 analysis_required; ASK ไม่ start analysis และไม่ admit message

How to read this draft: DB ใน chip หมายถึง raw file / persisted snapshot family, TB คือ derived validated analysis context/result และ FL คือ Chat-facing message/output; chip เป็น shorthand ในภาพเท่านั้น รายละเอียด authoritative อยู่ใน source map และโค้ดจริง ส่วน MITRE/RAG ถูกวาดเป็น optional augmentation เพราะไม่ใช่ core summarization evidence
