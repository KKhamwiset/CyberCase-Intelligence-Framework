🔗 เส้นทางการเชื่อมต่อไปยัง External API Provider

  • เส้นทางที่ 1 (OCR API): เมื่อพบไฟล์ภาพหรือ PDF สแกน Backend ส่งต่อไปให้ Typhoon OCR สกัดตัวอักษรภาษาไทย
  • เส้นทางที่ 2 (Core LLM): ใช้ประเมินช่องว่างข้อมูล (Gap Assessment) และวิเคราะห์สรุปคดีฉบับสมบูรณ์ (Main Analysis)
  • เส้นทางที่ 3 (GraphRAG): สื่อสารกับ RAG Service เมื่อตรวจพบพฤติการณ์โจมตีทางไซเบอร์ เพื่อดึงเทคนิค MITRE ATT&CK

Flow 02 · Document Intake & Ingestion (นำเข้า + OCR API)

แสดงขั้นตอนการรับเอกสาร การเชื่อมต่อไปยัง Typhoon OCR ภายนอก และการบันทึกจัดเก็บ

FLOW 02 · INGESTION
sequenceDiagram
    autonumber
    actor User as 👤 User (ผู้ใช้งาน)
    participant Backend as ⚙️ Backend (ระบบหลัก)
    participant DB as 🗄️ Database (ฐานข้อมูล)
    participant ExtAPI as 🧠 External API Provider

    User->>Backend: 1. อัปโหลดไฟล์เอกสาร (PDF, รูปถ่ายพยานหลักฐาน, หรือ DOCX)
    Note over Backend: ตรวจสอบความปลอดภัยและประเภทไฟล์ (MIME Type Detection)
    
    alt กรณีที่ 1: ไฟล์เป็นเอกสารสแกนหรือรูปภาพ (Scanned PDF / Images)
        Backend->>ExtAPI: 2a. ส่งภาพเอกสารไปสกัดข้อความ (Typhoon OCR API)
        Note over ExtAPI: ประมวลผลโมเดล OCR ภาษาไทยและภาษาอังกฤษ
        ExtAPI-->>Backend: 3a. ส่งคืนข้อความที่สกัดได้ + เลขหน้า + ค่าความมั่นใจ (Confidence)
    else กรณีที่ 2: ไฟล์เป็นเอกสารดิจิทัลปกติ (Native Digital PDF / DOCX)
        Backend->>Backend: 2b. สกัดข้อความตรงด้วยเครื่องมือภายใน (PyMuPDF / docx2txt)
    end

    Backend->>Backend: 4. บันทึกข้อมูลที่มาของเอกสาร (Provenance JSON & Page Spans)
    
    Backend->>DB: 5. บันทึกเอกสารลงตาราง `case_sources`
    Backend->>DB: 6. ปรับเพิ่มเลขเวอร์ชันพยานหลักฐานของคดี (`Case.source_revision` + 1)
    DB-->>Backend: 7. ยืนยันการจัดเก็บพยานหลักฐานสำเร็จ
    
    Backend-->>User: 8. แจ้งผลสำเร็จ พร้อมแสดงเนื้อหาข้อความที่สกัดได้บนหน้าจอ

🔍 การเชื่อมต่อกับ External OCR Provider

  • Typhoon OCR API: รองรับการอ่านเอกสารทางราชการไทย เอกสารลายมือชื่อ และตรายางประทับ
  • Graceful Fallback: หากเอกสารเป็น Text อยู่แล้ว ระบบจะไม่ยิง External API เพื่อประหยัดค่าใช้จ่ายและเวลา
  • Audit Trail: เก็บค่า Provenance ไว้ครบถ้วนว่าคำไหนมาจากหน้าใด และสกัดด้วยวิธีใด (Native หรือ OCR)

Flow 03 · Case Analysis & Clarification Gating (วิเคราะห์คดี)

แสดงขั้นตอนการเรียก External AI 2 จังหวะ: ประเมิน Gap และ สรุปคดี พร้อมการสืบค้น MITRE RAG

FLOW 03 · ANALYSIS
sequenceDiagram
    autonumber
    actor User as 👤 User (ผู้ใช้งาน)
    participant Backend as ⚙️ Backend (ระบบหลัก)
    participant DB as 🗄️ Database (ฐานข้อมูล)
    participant ExtAPI as 🧠 External API Provider

    User->>Backend: 1. กดปุ่ม "สั่งวิเคราะห์สำนวนคดี" (Analyze Case)
    Backend->>DB: 2. ดึงหลักฐานและประวัติคำตอบเดิม (Short DB Read Transaction)
    DB-->>Backend: 3. ส่งข้อมูลหลักฐานและประวัติคำตอบ (Source Bundle)
    Note over Backend, DB: ปิด DB Transaction ทันทีเพื่อไม่ให้ Connection ค้างระหว่างรอ AI

    %% Step 1 to External LLM
    Backend->>ExtAPI: 4. ส่งเอกสารให้ AI ประเมินหาช่องว่างข้อมูล (Core LLM: case_assessment_v1)
    ExtAPI-->>Backend: 5. ส่งรายการช่องว่างข้อมูลที่พบ (Unresolved Gaps Trace)

    Backend->>Backend: 6. ประเมินนโยบาย (Deterministic Policy): มี Gap สำคัญ และยังไม่เกินโควตาคำถามหรือไม่?

    alt กรณีที่ 1: พบ Gap สำคัญที่ต้องถาม (Decision = ASK)
        Backend->>DB: 7a. บันทึกคำถามข้อสงสัยลงในฐานข้อมูลแชท (ChatMessage)
        DB-->>Backend: 8a. บันทึกสำเร็จ
        Backend-->>User: 9a. หยุดวิเคราะห์ชั่วคราว + ส่งการ์ดคำถามให้ผู้ใช้ในแชท (Early Exit)
        Note over User, Backend: ตัดจบเร็ว! ประหยัดค่า Token เพราะไม่เรียก Main Analysis โดยไม่จำเป็น
    else กรณีที่ 2: ข้อมูลครบถ้วน หรือถามครบโควตาแล้ว (Decision = PROCEED)
        opt คดีตรวจพบพฤติการณ์โจมตีทางไซเบอร์
            Backend->>ExtAPI: 7b. สอบถามข้อมูลภัยคุกคามทางเทคนิค (GraphRAG: POST /query)
            ExtAPI-->>Backend: 8b. ข้อมูลเทคนิคและรูปแบบพฤติการณ์ของคนร้าย (MITRE ATT&CK Context)
        end
        %% Step 2 to External LLM
        Backend->>ExtAPI: 9b. สั่ง AI วิเคราะห์และสรุปสำนวนคดีฉบับสมบูรณ์ (Core LLM: main_case_analysis_v1)
        ExtAPI-->>Backend: 10b. ผลวิเคราะห์คดี (Summary, Parties, Timeline, Findings)
        Backend->>Backend: 11b. ตรวจสอบคำพูดอ้างอิง (Exact Quote) กับเอกสารจริง ถ้าไม่ตรงให้ตัดทิ้ง
        Backend->>DB: 12b. บันทึกผลวิเคราะห์ที่ผ่านการรับรองลงตาราง `case_analysis_results`
        DB-->>Backend: 13b. บันทึกสำเร็จ
        Backend-->>User: 14b. แสดงผลสรุปคดีและไทม์ไลน์เหตุการณ์บนหน้าจอ
    end

💡 การโต้ตอบกับ External API Provider ในขั้นตอนวิเคราะห์

  • จังหวะที่ 1 (Gap Assessment): เรียก LLM ขนาดเล็ก/เร็ว เพื่อตรวจหาเฉพาะประเด็นที่ยังขาดหาย
  • จังหวะที่ 2 (MITRE RAG): เรียก RAG Service เพื่อดึงเทคนิคการโจมตีจาก Qdrant/Neo4j มาใส่ในภาคผนวก
  • จังหวะที่ 3 (Main Analysis): เรียก LLM ประมวลผลรอบสุดท้ายเพื่อสรุปคดี ข้อเท็จจริง และลำดับเหตุการณ์

        Backend->>DB: 4a. บันทึกคำตอบของผู้ใช้ ผูกเข้ากับรหัสคำถามเดิม (Synthetic QA Key)

        Backend->>DB: 5a. ตรวจสอบโควตาคำถามที่ตอบไปแล้วในรอบนี้
        
        alt ยังไม่ครบโควตาของรอบ (เช่น ตอบ 1 จาก 3 คำถาม)
            Backend->>ExtAPI: 6a. สั่ง AI ประเมินหาคำถามข้อถัดไป (Core LLM)
            ExtAPI-->>Backend: 7a. คำถามข้อสงสัยข้อถัดไป
            Backend->>DB: 8a. บันทึกคำถามใหม่ลงในแชท
            Backend-->>User: 9a. แสดงคำตอบที่ส่งไป + ส่งการ์ดคำถามข้อถัดไปให้ตอบ
        else ตอบครบโควตาของรอบแล้ว (เช่น ตอบครบ 3 คำถาม)
            Backend->>ExtAPI: 6b. สั่ง AI วิเคราะห์คดีใหม่ทั้งหมด โดยรวมคำตอบทั้งหมดที่ได้รับ (Core LLM)
            ExtAPI-->>Backend: 7b. ผลการวิเคราะห์คดีฉบับปรับปรุงใหม่
            Backend->>DB: 8b. บันทึกผลวิเคราะห์ใหม่ลงในฐานข้อมูล
            Backend-->>User: 9b. แจ้งเตือนว่าตอบครบแล้ว พร้อมอัปเดตผลสรุปคดีฉบับใหม่ทันที
        end

    else กรณีที่ 2: ผู้ใช้ซักถามข้อสงสัยเกี่ยวกับคดีทั่วไป (Case Ask / Inquiry)
        Backend->>DB: 4b. ดึงผลวิเคราะห์และหลักฐานของคดีมาเป็นบริบท
        DB-->>Backend: 5b. ข้อมูลบริบทคดี
        Backend->>ExtAPI: 6c. สั่ง AI ตอบคำถามโดยอ้างอิงจากข้อมูลคดีเท่านั้น (Core LLM: Strict Grounding)
        ExtAPI-->>Backend: 7c. คำตอบที่อ้างอิงจากพยานหลักฐาน
        Backend->>DB: 8c. บันทึกข้อความคำถามและคำตอบลงในฐานข้อมูลแชท
        Backend-->>User: 9c. แสดงข้อความคำตอบของ AI ในหน้าต่างแชททันที
    end

💬 การเรียกใช้ External LLM ในระบบแชท

  • ตอบ Gap ถัดไป: เรียก AI เลือกคำถามที่มีความสำคัญสูงถัดไปจาก Assessment เดิม
  • วิเคราะห์รอบใหม่ (Re-analysis): เรียก AI วิเคราะห์คดีใหม่เมื่อผู้ใช้ตอบครบโควตารอบ (3 คำถาม)
  • ซักถามคดี (Case Ask): เรียก AI ตอบคำถามเฉพาะหน้า โดยจำกัดให้ตอบจากหลักฐานในคดีเท่านั้น

📊 ข้อกำหนดการใช้งาน

Clarification Responseผูกกับ Gap Key สำหรับวิเคราะห์รอบถัดไป
Case Inquiryตอบทันทีใน Request เดียว
Max Roundsสูงสุด 3 รอบต่อคดี (คุมงบประมาณ)
Grounded Answersต้องมี Source Citation กำกับ

🛡️ ทำไมขั้นตอนออกรายงานจึงไม่เรียก External AI?

  • ป้องกันการบิดเบือน: ผลการวิเคราะห์ได้ผ่านการตรวจสอบ (Source Binding) มาแล้ว การประกอบเล่มรายงานจึงต้องใช้แม่แบบตายตัว
  • ความถูกต้อง 100%: ทั้งหน้าเว็บและ PDF พิมพ์จากข้อมูลเดียวกัน ไม่มีความเสี่ยงที่ AI จะสุ่มคำใหม่
  • ความรวดเร็ว: การเรนเดอร์ PDF เกิดขึ้นทันทีในหลักวินาทีโดยไม่ต้องรอคิวโมเดลภายนอก

📋 สรุป 4 เสาหลักการออกแบบ

1. Source Trustหลักฐานคดีเท่านั้นที่เป็นความจริง
2. Early Exitตัดจบเร็วเพื่อประหยัดค่า Token
3. Short DB Txไม่ค้าง DB Connection ระหว่างรอ AI
4. Quote Bindingตัดคำอ้างอิงที่ไม่มีจริงในเอกสารทิ้ง

🧠 กลไกสำคัญของ GraphRAG Pipeline

  • Hybrid Vector + Graph: Qdrant ค้นหาความคล้ายคลึงของคำ และ Neo4j ช่วยขยายความสัมพันธ์ Tactics และ Mitigations ที่เกี่ยวข้อง 2-Hop
  • Query Decomposition: แตกพฤติการณ์ซับซ้อนเป็นประเด็นย่อยรายเทคนิค เพื่อให้ดึงข้อมูลได้ครบถ้วน ไม่ตกหล่น
  • Self-Reflection (Broaden Loop): ประเมินความเพียงพอของ Context ถ้าขาดหายจะเขียน Query ใหม่และสืบค้นซ้ำ (จำกัดสูงสุด 2 รอบ)

🛡️ การทำงานร่วมกับ Backend

  • Non-blocking Execution: `GraphRAGAgent.query()` ใช้เวลาประมาณ 10-30 วินาที จึงรันผ่าน `anyio.to_thread` ไม่ให้บล็อก FastAPI Backend
  • Entity Lookup Fail-Safe: หาก Neo4j มีปัญหาในการดึงชื่อเทคนิค ระบบจะใช้ข้อมูลจาก Vector Search มาทดแทน ไม่ทำให้ Request พัง
  • Source Role Isolation: ผลลัพธ์ทั้งหมดถูกเก็บใน `technical_context` ของรายงาน ไม่ถูกนับเป็นพยานหลักฐาน (Case Source)
