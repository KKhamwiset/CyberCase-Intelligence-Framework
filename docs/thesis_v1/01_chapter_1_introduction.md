# บทที่ 1 บทนำ

## 1.1 ความเป็นมาและความสำคัญของโครงงาน

ข้อมูลในสำนวนหรือข้อมูลเหตุการณ์มักเริ่มจากคำบรรยายที่มีความยาว รูปแบบไม่สม่ำเสมอ และมาจากหลายช่วงเวลา การทบทวนข้อมูลประเภทนี้ไม่ได้มีเพียงงานสรุปข้อความ แต่ต้องรักษาความสัมพันธ์ระหว่างข้อความต้นทาง ข้อที่ผู้ให้ข้อมูลรายงาน สิ่งที่ยังไม่ทราบ ข้อขัดแย้ง และข้ออนุมานที่ผู้วิเคราะห์สร้างขึ้น หากระบบรวมองค์ประกอบเหล่านี้เป็นคำตอบที่อ่านลื่นเพียงก้อนเดียว ผู้ใช้ย่อมตรวจได้ยากว่าข้อความใดมีที่มาจากสำนวนและข้อความใดเป็นเพียงการตีความ

แบบจำลองภาษาขนาดใหญ่ (Large Language Model: LLM) มีความสามารถในการสร้างและเรียบเรียงข้อความตามคำสั่ง แต่ความคล่องของภาษามิได้ทำให้ทุกข้อความที่สร้างขึ้นมีหลักฐานรองรับ งานด้าน factuality แสดงให้เห็นว่าการประเมินข้อความยาวควรแยกเป็นข้ออ้างย่อยและตรวจการสนับสนุนของแต่ละข้อ แทนการให้คะแนนความถูกต้องแก่ข้อความทั้งย่อหน้า [@min2023factscore; @scire2024fenice] งานด้าน attributed generation ยังเน้นว่าการมี citation ไม่เพียงพอ หาก citation ไม่รองรับข้อความที่อ้างหรือครอบคลุมข้ออ้างไม่ครบ [@rashkin2023measuring; @gao2023alce] หลักการดังกล่าวมีความสำคัญต่อบริบทสำนวน เพราะข้อเท็จจริง ข้อสันนิษฐาน และข้อมูลภายนอกมีน้ำหนักไม่เท่ากัน

CyberCase เริ่มต้นจากปัญหาการวิเคราะห์เหตุการณ์ความมั่นคงปลอดภัยไซเบอร์ ซึ่งมักต้องเชื่อมพฤติกรรมที่ปรากฏในคำบรรยายกับความรู้ทางเทคนิค เช่น tactics และ techniques ใน MITRE ATT&CK ระบบจึงพัฒนาบริการค้นคืนแบบผสมซึ่งใช้ฐานข้อมูลเวกเตอร์และกราฟเพื่อจัดเตรียมบริบทภายนอก อย่างไรก็ตาม ความรู้จาก ATT&CK อธิบายรูปแบบพฤติกรรมของผู้โจมตีในโลกไซเบอร์ มิใช่หลักฐานว่าเหตุการณ์เฉพาะคดีเกิดขึ้นจริง การออกแบบปัจจุบันจึงกำหนดให้ข้อมูล MITRE มีบทบาทเป็น external technical context เท่านั้น

เมื่อขอบเขตโครงงานขยายจากเหตุการณ์ไซเบอร์สู่การทบทวนข้อมูลคดีทั่วไป โครงสร้างหลักของการวิเคราะห์ต้องไม่บังคับให้ทุกคดีมี attacker, asset, technique หรือ timeline แบบเหตุการณ์ระบบคอมพิวเตอร์ โมดูล Main Case Analysis ใน working tree ปัจจุบันจึงใช้คำสั่งแบบ domain-neutral และจัดผลเป็น analytical claims ที่มีประเภทและสถานะทางญาณวิทยา (epistemic status) พร้อมรหัสข้อความที่สนับสนุนหรือขัดแย้ง ส่วน gap analysis และการเลือกคำถามขอข้อมูลเพิ่มยังเป็น stage แยกต่างหาก การเปลี่ยนผ่านนี้ยังไม่เสร็จสมบูรณ์ เนื่องจาก frontend และ report readers บางส่วนยังอ่านโครงสร้าง AnalysisTrace รุ่นก่อน

ด้วยเหตุนี้ แกนสำคัญของ CyberCase มิใช่การสร้าง chatbot สำหรับถามตอบเกี่ยวกับคดี แต่เป็นการออกแบบ workflow ที่จัดชั้นความน่าเชื่อถือของข้อมูล ทำให้ผลวิเคราะห์ตรวจย้อนกลับได้ จำกัดบทบาทความรู้ภายนอก และคงสถานะของการวิเคราะห์ไว้ในระบบ ระบบยังใช้การสนทนาเป็นพื้นผิวการโต้ตอบ แต่การประมวลผลเบื้องหลังประกอบด้วยการสร้าง raw evidence การค้นคืนบริบท การวิเคราะห์หลัก การประเมินช่องว่าง การถามข้อมูลเพิ่ม และการสร้างรายงานจาก snapshot ที่บันทึกไว้

## 1.2 ปัญหาที่ต้องการแก้ไข

ปัญหาแรกคือข้อมูลคดีแบบข้อความไม่มีโครงสร้างเดียวกัน รายละเอียดบุคคล เหตุการณ์ เวลา สถานที่ และผลกระทบอาจกระจายอยู่หลายข้อความ การสรุปที่ไม่รักษารหัสแหล่งที่มาทำให้ผู้ใช้ต้องค้นย้อนกลับด้วยตนเอง และเพิ่มความเสี่ยงที่ข้อสรุปจะถูกอ่านโดยไม่เห็นบริบทเดิม

ปัญหาที่สองคือการแยก “สิ่งที่รายงาน” ออกจาก “สิ่งที่ระบบอนุมาน” ในภาษาธรรมชาติ ข้อความที่เขียนอย่างมั่นใจอาจเป็นเพียงความเป็นไปได้ ขณะที่คำว่า “ไม่ทราบ” อาจถูกระบบทั่วไปตีความเป็นข้อมูลที่ขาดและถามซ้ำ ทั้งที่ผู้ใช้ได้แจ้งชัดแล้วว่าไม่มีข้อมูล CyberCase จึงต้องมีประเภท claim, epistemic status และ gap taxonomy ที่สื่อความแตกต่างเหล่านี้ในโครงสร้างข้อมูล

ปัญหาที่สามคือการรักษาขอบเขตหลักฐาน เมื่อระบบใช้ RAG คำอธิบายจากคลังความรู้มีประโยชน์ต่อการตีความ แต่ไม่ควรถูกเลื่อนสถานะเป็นข้อเท็จจริงของคดี เช่น ความรู้ว่าเทคนิคหนึ่งมักเกี่ยวข้องกับพฤติกรรมบางแบบ ไม่ได้พิสูจน์ว่าผู้กระทำในคดีใช้เทคนิคนั้นจริง ระบบต้องแสดง association ในฐานะ candidate หรือ external context และผูกเหตุผลกลับไปยัง claim ที่มาจาก raw evidence

ปัญหาที่สี่คือการถามข้อมูลเพิ่มอย่างมีขอบเขต คำถามจำนวนมากทำให้ผู้ใช้เสียภาระและอาจขยายคดีเกินความจำเป็น แต่การไม่ถามเลยอาจทำให้ระบบตอบบนข้อมูลที่กำกวม การออกแบบจึงต้องเลือกเฉพาะ gap ที่มีความสำคัญและถามได้ หลีกเลี่ยงคำถามซ้ำ และไม่ถามข้อมูลที่ผู้ใช้ระบุว่าไม่ทราบหรือไม่มีอยู่

ปัญหาที่ห้าคือการสร้างรายงานอย่างทำซ้ำได้ หากการสร้างรายงานเรียก LLM ใหม่ทุกครั้ง เนื้อหาอาจเปลี่ยนแม้ข้อมูลคดีไม่เปลี่ยน CyberCase จึงใช้ snapshot, hash, version และ idempotency ร่วมกับแม่แบบ deterministic เพื่อให้การสร้างรายงานจากสถานะเดียวกันมีขอบเขตที่ตรวจสอบได้

## 1.3 วัตถุประสงค์ของโครงงาน

1. เพื่อพัฒนาเว็บแอปพลิเคชันสำหรับบันทึกและทบทวนข้อมูลคดีในรูปการสนทนาที่มี persistence
2. เพื่อพัฒนาโมดูลวิเคราะห์ด้วย LLM ที่สร้างข้อความวิเคราะห์พร้อม AnalysisTrace แบบมีโครงสร้าง และแยกข้อมูลรายงาน ข้ออนุมาน และสิ่งที่ยังไม่ทราบ
3. เพื่อรักษาการตรวจสอบย้อนกลับระดับข้อความด้วย source message identifiers และ evidence digest
4. เพื่อประเมินช่องว่างของข้อมูลและสนับสนุนการถามคำถามขอข้อมูลเพิ่มแบบมีขอบเขต
5. เพื่อเชื่อมบริบท MITRE ATT&CK สำหรับคดีไซเบอร์โดยคงสถานะเป็นความรู้ภายนอก ไม่ใช่หลักฐานคดี
6. เพื่อสร้างรายงานแบบมีโครงสร้างจาก snapshot ที่บันทึกไว้ด้วยกระบวนการเชิงแม่แบบและ idempotency
7. เพื่อทดสอบองค์ประกอบซอฟต์แวร์ด้วย automated tests และจัดทำแผนการประเมินเชิงประจักษ์ที่ไม่เกินหลักฐานที่มี

วัตถุประสงค์ข้อ 1, 3, 4, 5 และ 6 มีหลักฐานการ implement ใน current checkout วัตถุประสงค์ข้อ 2 มี backend implementation v3 ใน working tree แต่การบูรณาการกับ frontend/report ยังไม่ครบ ส่วนข้อ 7 ทำได้ในระดับ unit/integration-style tests และ exploratory experiments ยังไม่ครอบคลุม expert evaluation หรือ live operational validation

## 1.4 ขอบเขตของโครงงาน

### 1.4.1 ขอบเขตที่ใช้งานแล้ว

- สร้าง เปิด เปลี่ยนชื่อ และลบ chat thread สำหรับข้อมูลคดี
- บันทึกข้อความผู้ใช้และผู้ช่วย ลำดับข้อความ และ metadata
- จัดการ analysis run แบบ background lease พร้อมสถานะและการป้องกัน active run ซ้ำ
- สร้าง raw evidence จากข้อความผู้ใช้ที่มีบทบาทเป็นข้อมูลคดี
- เรียก RAG service สำหรับ fresh analysis และบันทึก retrieval context
- สร้าง Main Case Analysis และผลที่มีโครงสร้าง
- ประเมิน gap และอาจถาม clarification ภายใต้รอบที่จำกัด
- ถามคำถามต่อผลวิเคราะห์โดยนำ analysis context ที่บันทึกไว้กลับมาใช้
- สร้าง จัดเก็บ ดูประวัติ และส่งออก PDF ของรายงานที่ผูกกับ chat

### 1.4.2 ขอบเขตของ Analysis Module

Analysis Module รับ raw evidence, previous validated analysis ในโหมด ask และ optional external context ตาม workflow ผลลัพธ์ปัจจุบันมีทั้งข้อความสำหรับผู้ใช้และ AnalysisTrace v3 ซึ่งมี summary, claims, gaps, MITRE associations, evidence hash และ retrieval-context binding อย่างไรก็ตาม provider schema ของ Main Analysis ยังไม่สร้าง gaps และ parser กำหนด `gaps=[]`; gap ที่ใช้ใน follow-up มาจาก stage แยกต่างหาก การรวม claim–evidence–gap เป็นแบบจำลอง canonical เดียวจึงอยู่ระหว่างการพัฒนา

### 1.4.3 ขอบเขต RAG/MITRE

RAG service ค้นความรู้ MITRE ATT&CK จาก Qdrant และ Neo4j และคืน retrieval context กับตาราง MITRE ให้ backend บริการนี้ยังเป็น cyber-specific และไม่ได้ใช้เป็น ontology สำหรับคดีทั่วไป ระบบไม่ถือข้อความที่ค้นคืนหรือคำตอบของแบบจำลอง RAG เป็นหลักฐานของคดี

### 1.4.4 ขอบเขตส่วนติดต่อผู้ใช้

พื้นที่ทำงานประกอบด้วย Intake, Overview, Case Materials, Technical Context, Chat และ Report มี source popover และ error modal เพื่อให้ผู้ใช้ตรวจแหล่งที่มาและเห็นข้อผิดพลาดในรูปแบบที่ปลอดภัย อย่างไรก็ดีผู้อ่าน v3 ในบางหน้าจอยังไม่สมบูรณ์

### 1.4.5 ขอบเขตเอกสารและรายงาน

ระบบมี document-ingestion preview สำหรับ PDF, DOCX, PNG และ JPEG ใน working tree ปัจจุบัน มี OCR แบบเต็มหน้า แต่ยังไม่บันทึกผลเข้าสำนวน ไม่ส่งเข้าการวิเคราะห์ และไม่รองรับ handwriting recognition ส่วนรายงานของระบบเป็น chat-scoped report ที่สร้างจาก persisted snapshot มิใช่ top-level case report API

### 1.4.6 สิ่งที่อยู่นอกขอบเขต

- การวินิจฉัยข้อกฎหมาย การตัดสินความผิด หรือคำแนะนำทางกฎหมายอัตโนมัติ
- Legal RAG และฐานความรู้กฎหมาย
- การแทนที่อัยการ ผู้สืบสวน ผู้ตรวจพิสูจน์ หรือผู้เชี่ยวชาญ
- การดำเนินกระบวนการ forensic โดยอัตโนมัติหรือการสั่งการระบบภายนอก
- authentication, authorization และการแยกข้อมูลตามผู้ใช้ในผลิตภัณฑ์ปัจจุบัน
- production deployment ที่ได้รับการยืนยัน
- OCR/HTR ที่นำผลเข้าสำนวนอัตโนมัติ โดยเฉพาะลายมือ
- การรับรองความถูกต้องทางกฎหมายหรือผลการใช้งานจริง

### ตารางที่ 1-1 ขอบเขตและสถานะของโครงงาน

| กลุ่ม | สถานะ | คำอธิบาย |
|---|---|---|
| Persisted chat workflow | ใช้งานแล้ว | มี models, migrations, routes และ tests |
| Cyber-specific MITRE enrichment | ใช้งานแล้ว | เป็น external context |
| General Main Analysis v3 | อยู่ใน working tree | backend ใช้งานและทดสอบแล้ว แต่ cross-layer integration ยังไม่ครบ |

| Claim–Evidence–Gap unified workflow | อยู่ระหว่างพัฒนา | สัญญาข้อมูลยังแยกระหว่าง v3 trace กับ follow-up gap |
| Legal RAG / legal decision | นอกขอบเขต | ไม่ได้ implement |
| Expert/product effectiveness study | ยังไม่ดำเนินการ | [RESULT PENDING] |

## 1.5 ประโยชน์ที่คาดว่าจะได้รับ

1. ได้ต้นแบบระบบที่จัดข้อมูลคดีและผลวิเคราะห์ไว้ใน workflow เดียว พร้อมประวัติและสถานะที่บันทึกได้
2. ได้กลไกที่ช่วยให้ผู้ใช้ตรวจว่าข้ออ้างเชิงวิเคราะห์อาศัยข้อความใด แทนการรับคำตอบของ LLM โดยไม่มีร่องรอย
3. ได้แนวทางแยกหลักฐานคดี ข้ออนุมาน และบริบทความรู้ภายนอกอย่างชัดเจนในระดับสัญญาข้อมูลและ prompt
4. ได้กลไก gap/follow-up ที่ลดการถามข้อมูลที่ผู้ใช้ระบุว่าไม่ทราบ และจำกัดจำนวนรอบการโต้ตอบ
5. ได้รายงานจาก persisted snapshot ที่มี version และ idempotency เหมาะกับการตรวจสอบซ้ำในระดับระบบต้นแบบ
6. ได้ฐาน code, tests, evidence ledger และแผนประเมินสำหรับพัฒนา Version ถัดไปอย่างตรวจสอบได้

ประโยชน์เหล่านี้เป็นประโยชน์ที่คาดหวังจากการออกแบบและผลการพัฒนาระบบ ไม่ใช่ผลการศึกษากับผู้ใช้งานจริง เนื่องจากยังไม่มีหลักฐานด้านเวลาที่ประหยัดได้ ความถูกต้องทางกฎหมาย หรือความพึงพอใจของอัยการและผู้สืบสวน
