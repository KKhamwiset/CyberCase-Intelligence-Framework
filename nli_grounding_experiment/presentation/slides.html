Problem & Motivation

The Grounding Dilemma in Threat Intel

ทำไม Generative LLM และ Vanilla RAG ถึงไม่เพียงพอสำหรับการสืบสวนคดีไซเบอร์

02 / 13
Hallucinated Attribution
LLMs มักจะ "จินตนาการ" ผู้ก่อเหตุ (Threat Actors) หรือระบุเทคนิค MITRE ATT&CK ที่เกินจริงจากหลักฐานในเอกสารคดีดิบ
Attention Dilution
เมื่อป้อนเอกสารหลักฐานขนาดยาว (Full Premise) เข้าโมเดล สมาธิของ Attention Mechanism จะเจือจาง ทำให้มองข้ามข้อเท็จจริงสำคัญ หรือปฏิเสธหลักฐานที่ถูกต้อง
Missing Trust Boundary
ระบบส่วนใหญ่ไม่มีด่านตรวจสอบทางคณิตศาสตร์ที่โปร่งใส การสรุปข้อความ (Judgement) รับข้อมูลดิบไปสรุปทันทีโดยไม่มีการรับรองความถูกต้อง
🛡️ The CyberCase Solution: Deterministic Evidence-Unit Grounding
แบ่งเอกสารออกเป็น Evidence Units (U001, U002...) ที่มี text hash และ char-offset แน่นอน จากนั้นบังคับให้โมเดลสร้าง Canonical Claims ผูกกับ Unit IDs และส่งผ่าน NLI Verification Engine ก่อนที่ผลการวิเคราะห์จะถูกส่งต่อไปยังขั้นตอน Judgement

⚡ The Golden Backend Rule: "Read Short. Think Free. Write Short."
เนื่องจากงาน AI Analysis ใช้เวลาประมวลผลนานหลายสิบวินาทีถึงหลายนาที การถือ Database Transaction ค้างไว้จะทำให้ Database Connection เต็มและ Lock ตารางทันที
# 1. Read Short (เสี้ยววินาที)
started = await read_case_for_analysis(...)

# 2. Think Free (โมเดลคิดอย่างอิสระ ไม่มี DB connection)
outcome = await think(pipeline, started)

# 3. Write Short (บันทึกผลเสร็จปิดทันที)
step = await store_outcome(...)
ผลลัพธ์: Pipeline ภายในเป็น Pure Stateless Functions — ทดสอบง่าย, รัน Benchmark แยกได้ และไม่มีปัญหา Deadlock

📖 Evidence Units vs. Claims
เอกสารต้นฉบับจะถูกหั่นเป็น Evidence Units ที่มี hash คงที่เสมอ Case Reading จะเลือกเฉพาะ Unit IDs ที่เกี่ยวข้องมาอ้างอิง หาก Claim ไหนไม่สามารถผูก (bind) กับ Unit ที่มีอยู่จริงได้ จะถูกลดสถานะเป็น not_confirmed ทันที
⚖️ Judgement Isolation

Core Innovation Spotlight

The NLI Grounding Verification Engine

Trust Boundary ด่านสำคัญ: ทำไมต้องใช้ Frozen NLI แทนที่จะใช้ Generative LLM Judge

05 / 13
🎯 The Verification Mission
ตัดสินอย่างเป็นวิทยาศาสตร์ว่า Claim ที่สกัดออกมาจากคดี ได้รับการสนับสนุน (Entailment) จากหลักฐานจริงหรือไม่:
[Premise: Filtered Evidence Units] + [Hypothesis: Claim]
    ↳ NLI Model ↳ [P(entail), P(neutral), P(contradiction)]
        ↳ Decision Layer ↳ SUPPORTED / UNSUPPORTED
  • ✓ Zero Generative Calls: ไม่มีค่าใช้จ่าย Token และไม่มีอาการ Hallucinate ซ้ำสอง
  • ✓ Deterministic & Auditable: ค่า Probability และ Feature ชัดเจน ตรวจสอบย้อนหลังได้ 100%
  • ✓ No Prompt Injection Risk: ข้อความมุ่งร้ายในเอกสารคดีไม่สามารถสั่งให้ NLI หลงกลได้
❌ ปัญหาของ LLM-as-a-Judge ทั่วไป
• ราคาสูง Latency นาน (หลายร้อยมิลลิวินาทีถึงระดับวินาทีต่อคู่ประโยค)
• มีความแปรปรวน (Non-deterministic) แม้ตั้ง Temperature = 0
• มี Positional Bias และความลำเอียงชอบเห็นด้วย (Sycophancy)
✓ จุดเด่นของ CyberCase NLI Pipeline
• Semantic Evidence Filter: กรองเฉพาะประโยคหลักฐานที่เกี่ยวข้องด้วย Sentence Embeddings ($\tau=0.20$)
• Frozen NLI Backbone: ใช้โมเดล Multilingual Pretrained ที่ผ่านการเทรนด้วย XNLI 2.7M ตัวอย่าง
• Task-Specific Decision Layer: ใช้ 3D Logistic Regression เพื่อปรับสมดุลความเชื่อมั่นของงานตรวจสอบคดี

Pipeline Ablation Design: From B0 to B4

การแยกแยะและควบคุมตัวแปรเพื่อหาคำตอบว่าชิ้นส่วนใดสร้างประโยชน์จริง

06 / 13
B0 Full Premise + Forward NLI → 1D DEV Threshold (θDEV)
ป้อนหลักฐานเต็ม → คำนวณ P(entailment) ≥ θDEV (θ จูนบน DEV Split)
B0-LR Full Premise + Forward [E, N, C] → 3D Logistic Regression
ใช้หลักฐานเต็ม แต่เปลี่ยนเป็น 3D LR Classifier Head (เทรนบน TRAIN split เท่านั้น)
B1 Semantic Filter (τ=0.20) + Forward NLI → 1D DEV Threshold (θDEV)
กรองเอาเฉพาะ Evidence Units ที่มี Cosine Similarity ≥ 0.20 ก่อนตัด threshold บน DEV
B1-LR Semantic Filter + Forward [E, N, C] → 3D LR (Official Champion)
รวมพลังของการตัดขยะ (Filtering) เข้ากับการเรียนรู้ขอบเขตการตัดสินใจ 3 มิติที่สมดุล
B2 Full Premise + Bidirectional NLI → 6D LR
รัน NLI 2 ทิศทาง (E ⇒ C และ C ⇒ E) บนเอกสารเต็ม ได้ 6 Probability Features
B3 Filtered Premise + Bidirectional NLI → 6D LR
รัน NLI 2 ทิศทางบนหลักฐานที่กรองแล้ว เพื่อดูว่า Reverse NLI ช่วยเพิ่มคะแนนไหม
B4 B3 + Temperature Scaling + Selective Gating
เพิ่ม Threshold ความมั่นใจสูงเพื่อปฏิเสธการตัดสินใจ (Selective Rejection)
เกณฑ์การประเมิน (Evaluation Rigor)
• จูน θ บน DEV Split (N=1,043) เท่านั้น และประเมินบน Held-out Test (N=1,070)
• ทดสอบนัยสำคัญด้วย Paired Bootstrap (Nboot = 1,000, Seed = 42, 95% CI)

Engineering Finding

Busting the "Reverse NLI" Assumption

ทำไม Bidirectional NLI ถึงไม่คุ้มค่าทางวิศวกรรมในระบบตรวจสอบคดีจริง

08 / 13
🔬 The Bidirectional Hypothesis ($B3$)
สมมติฐานเดิม: ถ้าเรารัน NLI ทั้งสองทิศทาง:
1. Forward: Evidence ⇒ Claim ($P_{\text{fwd}}$)
2. Reverse: Claim ⇒ Evidence ($P_{\text{rev}}$)
รวมกันเป็น 6 Features จะช่วยตรวจจับกรณีที่ Claim มีข้อมูลเกินจริงได้ดีขึ้น
สิ่งที่เกิดขึ้นจริงในการทดลอง (95% CI ครอบคลุม 0 ทั้งคู่):

• บน mDeBERTa-v3-base: Δ Macro-F1 = +0.0020 (95% CI: [-0.0065, +0.0113])
• บน multilingual-MiniLM-L6: Δ Macro-F1 = +0.0011 (95% CI: [-0.0153, +0.0179])
• ความแม่นยำแทบไม่ขยับ และช่วงความเชื่อมั่น 95% ครอบคลุมศูนย์ทั้งหมด

💸 Cost vs. Benefit Analysis
• Inference Overhead: ต้องประมวลผล NLI เพิ่มอีก 1 รอบ (Requires approximately twice the NLI inference passes)
• Memory & Complexity: Feature Vector ขยายจาก 3D เป็น 6D เพิ่มความเสี่ยง Overfitting
• Statistical Verdict: ไม่พบหลักฐานที่น่าเชื่อถือทางสถิติว่า Reverse NLI มอบข้อมูลเสริมที่เป็นประโยชน์ (95% CI ครอบคลุมศูนย์)
🛡️ The Decision: Occam's Razor Wins
CyberCase ตัดสินใจเลือก B1-LR (Forward-Only) เป็น Production Champion เพราะให้ผลลัพธ์เทียบเท่ากันในเชิงสถิติ (Statistically indistinguishable) โดยไม่ต้องเสีย NLI inference pass รอบสอง และโค้ดเรียบง่ายกว่ามาก
